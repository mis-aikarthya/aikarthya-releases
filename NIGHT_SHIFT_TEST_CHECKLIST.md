# Night Shift — M&E Management Console Test Checklist

Branch: `night-shift/me-mgmt-dashboard` · Issues AIK-5 through AIK-27 (Done, `needs-review`)

## Before you start (read once)

- **Two surfaces to test.** Almost everything below is the **Management Console** — run the Flutter app on **Chrome / desktop web**, sign in as an **mgmt** (or `me_associate`) user, land on `/mgmt/home`. Only AIK-13 (location capture) is tested on the **PF Android device**.
- **Backend matters.** The location-trail features (current-location table, trail map, event timeline) only show data if the `location_pings` migration (AIK-6) is applied to the backend the build points at, **and** a PF device (AIK-13) has actually been moving and checked in for a while. On fresh staging these will legitimately be **empty** — that's "needs data", not "broken". Note which case you see.
- **Mark each item:** ✅ works / ⚠️ works-but (note it) / ❌ broken / ⏳ needs-data-or-config. Put detail in the Feedback line.

## Issue: AIK-6 (F1 location_pings migration) + AIK-13 (F2 mobile 30-min capture) — backend + device
- What was implemented: **F1** — new `location_pings` table (+ RLS + index) via a staging migration in `aikarthya-supabase`. **F2** — the **PF mobile app** captures a location fix ~every 30 min while checked in and writes a `location_pings` row (with `attendance_id`), delivered through the existing `sync_outbox` (offline-safe). ⚠️ Background reliability is a **known ceiling** — not guaranteed exact-30-min on all Android OEMs.
- How to test: This one is **not a console visual check** — it's the data source for everything location-based above. (1) **Migration:** confirm `location_pings` exists in the backend the app points at (staging now; **must also be applied to prod before launch**). (2) **Device:** on a **real PF Android device**, sign in as a PF, **check in**, and keep the app running while moving around for an hour+. Confirm new `location_pings` rows appear (check Supabase, or watch the Overview current-location table / WDR trail populate). Test offline behavior: lose signal, confirm pings queue in `sync_outbox` and **flush on reconnect**. Note the real capture interval and whether backgrounding/locking the phone stops capture (the known reliability ceiling). Without this step, AIK-26/14, AIK-27, AIK-25 will all read as empty.
